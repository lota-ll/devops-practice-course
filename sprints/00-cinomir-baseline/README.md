# Спринт 00: cinomir — baseline

> **Сценарій:** spike довів, що Сільпо, Фора і Novus віддають ціни, наявність і штрихкоди. Тепер прототип треба перетворити на сервіс: бот у Telegram відповідає за кілька секунд, падіння однієї мережі не ламає відповідь, усе піднімається однією командою, а кожен коміт проходить CI і дає образ у реєстрі.
> **Чому зараз:** усі наступні спринти (Terraform, Kubernetes, Helm, GitOps, EKS) розгортають саме цей застосунок. Слабкий baseline = біль у кожному наступному спринті.
> **Вхідний рівень:** Python, Docker, Docker Compose, GitHub Actions на базовому рівні, SQL.
> **Результат:** репозиторій `cinomir` з api + worker + bot, Compose-середовищем, тестами і CI, що публікує образ у GHCR і промоутить його в `staging` після approve.
> **Час:** теорія ~1,5 год · практика ~12 год · break-it ~1,5 год
> **Вартість AWS:** $0

## 📚 Мінімум теорії

### Один образ — кілька процесів

Як ресторан: одна кухня (код), але кухар, офіціант і посудомийник роблять різне. `api`, `worker` і `bot` — той самий образ з різною командою запуску. Одна збірка, один скан вразливостей, одна версія в усіх процесах.
**Де трапиться:** Compose (`command:`), у спринті 02 — три Deployment з одним `image:`.

### Liveness ≠ readiness

`/healthz` відповідає на питання «процес живий?» — якщо ні, його треба перезапустити. `/readyz` — «чи можна слати трафік?»: якщо PostgreSQL недоступний, перезапуск api не допоможе, а от прибрати под з балансування — так. Тому `/healthz` **не перевіряє залежності**, інакше падіння БД перезапустить усі поди одночасно.
Мережі (Сільпо, Фора, Novus) **не входять** у readiness: їх падіння — не наша проблема, ми показуємо часткову відповідь.

### Зовнішні залежності, які не контролюєш

Три сторонні API = три джерела затримок і збоїв. Правила:
- **таймаут на кожен виклик** (не один спільний на весь пошук);
- **обмеження паралельності** на мережу (семафор), щоб не створювати навантаження;
- **часткова відповідь** краще за помилку: «⚠️ Фора: не відповіла вчасно» + результати двох інших;
- **не кешувати повну невдачу**, інакше наступний запит отримає ту саму порожнечу з кешу.

### Повільну роботу — у фон

Сільпо не віддає штрихкод у пошуку — лише в картці товару, окремим запитом на кожен. 20 карток під час пошуку = користувач чекає. Рішення: api кладе id у чергу Redis, `worker` дозбирує повільно, наступні пошуки вже зіставляють товари. Класичний патерн «producer → queue → consumer».

### Long polling і «лише один бот»

Бот питає Telegram «є нові повідомлення?» (`getUpdates`). Два процеси з одним токеном одночасно — Telegram відповідає другому `409 Conflict`. Тому бот — **рівно один екземпляр**, і це перше обмеження, яке ми знімемо у спринті 03 (webhook).

### Міграції — окремим кроком

Міграція при старті api = гонка, коли піднімається 3 репліки. Тому міграції — one-shot контейнер `migrate`, а api/worker стартують після його успішного завершення. У Kubernetes це стане Job (спринт 02) і Helm hook (спринт 03).

### Build once, deploy many

Образ збирається **один раз** і отримує тег `sha-<commit>`. Промоут у `staging` — це новий тег того самого образу, а не нова збірка: що протестовано, те й розгорнуто.

📖 Один первинний ресурс: [The Twelve-Factor App](https://12factor.net/) — розділи III (Config), VI (Processes), IX (Disposability), XI (Logs).

### Задача 2 (1,5 год): Дані та міграції

> 💡 **Навіщо:** історія цін — єдине, що не можна відновити, якщо втратити. Схема змінюється лише міграціями, які CI перевіряє на справжньому PostgreSQL.

- `products`: мережа, id товару в мережі (**унікальна пара**), назва, фасовка (сирий текст + кількість у г/мл), штрихкод, джерело штрихкоду, slug, url, `first_seen` / `last_seen`, `ean_checked_at`
- `price_snapshots`: товар (FK, `ON DELETE CASCADE`), час, ціна (`Numeric`, не `Float`!), стара ціна, акція, наявність, залишок; індекс `(product_id, observed_at)`
- async SQLAlchemy 2.x; **один URL** `postgresql+psycopg://…` для застосунку і для Alembic (psycopg 3 вміє обидва режими)
- Alembic: `env.py` бере URL з `DATABASE_URL`; перша міграція написана **вручну** або згенерована і перечитана

✅ **Перевірка:** `alembic upgrade head && alembic check && alembic downgrade base && alembic upgrade head` — без помилок; `alembic check` пише `No new upgrade operations detected`.

### Задача 3 (2,5 год): Адаптери мереж

> 💡 **Навіщо:** кожна інтеграція зі стороннім API має однаковий контракт. Додати METRO (той самий zakaz.ua) чи АТБ у майбутньому = ще один клас, без змін у сервісі пошуку.

- абстрактний `Chain`: `name`, `title`, `async search(client, query, limit)`, `async fetch_barcodes(client, slug)` (за замовчуванням — порожньо)
- спільна модель пропозиції: ціна, стара ціна, фасовка, штрихкод, акція, `in_stock` (`None` = мережа не каже), залишок, url
- `Silpo`, `Fora`, `Novus` — параметри з описом [джерел даних](../../docs/project-cinomir.md#джерела-даних); ідентифікатори магазинів — з оточення (Київ за замовчуванням)
- розпізнавання Cloudflare (`403/429/503` + `cf-ray` / `server: cloudflare`) → `BlockedError`; неочікувана структура відповіді → `ChainError`
- чисті функції в окремому модулі: розбір фасовки (`2*80г` → 160 г; `62.50 грн` — **не** грами), релевантність (перше слово обов'язкове, префікси, латинські двійники кирилиці), GTIN (нормалізація до 13 цифр, контрольна цифра, внутрішні коди `020–029` пропускаємо, GTIN-14 ящика — лише в крайньому разі)
- тести **без мережі**: `httpx.MockTransport` і зразки відповідей

✅ **Перевірка:** `make test` — зелений; `relevance("тунець у власному соку", "Корм Whiskas з тунцем")` < 0.6; Novus `"04820235630591"` і Сільпо `"4820235630591"` дають однаковий штрихкод.

### Задача 4 (2,5 год): Сервіс пошуку та API

> 💡 **Навіщо:** серце системи — паралельні виклики, таймаути, деградація, кеш. Те, про що питають на співбесідах під виглядом «як ти інтегрувався із зовнішнім API».

Сервіс пошуку:
- `search_id` = хеш нормалізованого запиту **і конфігурації магазинів** (інший магазин = інший кеш)
- у мережі — лише головне слово запиту; точність — локальний фільтр релевантності
- `asyncio.gather` по мережах; на кожну — семафор і `wait_for(timeout)`; статус кожної мережі у відповіді (`ok`, отримано, релевантних, мс, помилка людською мовою)
- upsert товарів + знімок ціни на кожну пропозицію; id товарів Сільпо без штрихкоду — у чергу (без дублікатів, не частіше ніж раз на N днів)
- групи «той самий товар у різних мережах»: union-find за `ean:…` та спільним id Сільпо/Фори; економія — лише між товарами **в наявності**
- кеш у Redis з TTL; результат, де впали **всі** мережі, не кешується

API (FastAPI, фабрика `create_app()` з `lifespan`):
- ендпоінти з таблиці [API](../../docs/project-cinomir.md#api); валідація параметрів (`q` 2–100 символів, `sort` ∈ `price|unit`)
- пагінація і сортування — з кешу; сортування `unit` рахує ціну за кг/л, але **показуємо лише ціну і вагу**
- middleware: метрика і JSON-лог на кожен запит, **`path` = шаблон маршруту**, а не сирий URL
- `/readyz` → `503`, якщо PostgreSQL або Redis недоступні

✅ **Перевірка:** тести з fakeredis + SQLite проходять; другий однаковий запит повертає `"cached": true` і не робить запитів у мережі; `/metrics` не містить `search_id` у labels.

### Задача 5 (2 год): Воркер і бот

> 💡 **Навіщо:** фонові процеси і graceful shutdown — те, що ламається першим у Kubernetes, якщо зроблено неправильно.

Воркер:
- `BRPOP` з коротким таймаутом (швидка реакція на SIGTERM), обробник `SIGTERM`/`SIGINT` → акуратний вихід
- штрихкод з картки Сільпо → той самий штрихкод товару Фори з тим самим id
- пауза між запитами; `BlockedError` → пауза 60 с; будь-яка інша помилка → лог + коротка пауза (без гарячого циклу)
- метрики на окремому порту

Бот (aiogram 3, long polling):
- **allowlist** як outer middleware: чужий користувач отримує «⛔ Доступ обмежено. Ваш Telegram id: N»
- текст → API → повідомлення: ціна (стара перекреслена), вага, мережа, акція; попередження про мережі, що не відповіли; блок «той самий товар у різних мережах»
- кнопки ◀️ ▶️ і перемикач «⚖️ вигідніше за вагою» / «💰 за ціною»; `callback_data` ≤ 64 байт
- `parse_mode=HTML` → **усе з мереж екранується** (`html.escape`)
- форматування — чисті функції в окремому модулі (тестуються без Telegram)

✅ **Перевірка:** SIGTERM воркеру → у лозі `worker stopped` за ≤ 3 с; тест: назва товару `A & B <script>` приходить екранованою.

### Задача 6 (1,5 год): Контейнери та Compose

> 💡 **Навіщо:** `docker compose up` — це «локальний Kubernetes для бідних». Ті самі ідеї (healthcheck, порядок старту, one-shot задачі) стануть probes, Job і hooks.

- multi-stage `Dockerfile`: шар залежностей кешується окремо від коду; runtime без компіляторів; **non-root** (UID 10001); `HEALTHCHECK`
- `.dockerignore` (без `.git`, `.env`, тестів, кешів)
- Compose: `postgres` і `redis` з healthcheck · `migrate` (one-shot) · `api` і `worker` стартують після `service_completed_successfully` · `bot` — у профілі `bot` і після `service_healthy` для api · порти БД і API — лише на `127.0.0.1`
- YAML-якорі замість копіювання середовища між сервісами

✅ **Перевірка:** `make up` → `make search Q="тунець у власному соку"` → результати трьох мереж; `docker compose exec api id -u` → `10001`; додай токен у `.env`, `make up-bot` → бот відповідає тобі.

### Задача 7 (1,5 год): CI/CD

> 💡 **Навіщо:** «працює на моєму ноутбуці» перестає бути аргументом. Кожен PR перевірено, кожен образ просканований, промоут контрольований.

Workflow на `pull_request` і `push` у `main`:
1. `lint` — ruff check + format check
2. `test` — pytest, JUnit-звіт як артефакт
3. `migrations` — service-контейнер PostgreSQL: `upgrade → check → downgrade → upgrade`
4. `build` (після 1–3) — buildx з кешем GHA, smoke-тест образу (імпорт модулів, `id -u` = 10001), **Trivy** (CRITICAL/HIGH з виправленням = падіння), push `ghcr.io/<you>/cinomir:sha-xxxxxxx` лише з `main`
5. `promote-staging` — GitHub Environment `staging` з **required reviewer**; retag `sha-…` → `staging` без перезбирання

`permissions:` мінімальні на рівні workflow, розширення — лише в job, де потрібно.

✅ **Перевірка:** PR з порушенням ruff — червоний; merge у `main` → образ у GHCR → job `promote-staging` чекає approve → після approve з'являється тег `staging` з тим самим digest.

| 8 | Прибери `USER 10001` з Dockerfile | Smoke-тест у CI падає | Лог job `build` |

## ⚠️ Типові помилки

| Симптом | Причина | Фікс |
|---|---|---|
| `MissingGreenlet` / `greenlet_spawn has not been called` | Ліниве завантаження зв'язку в async-сесії (`product.snapshots.append`) | `flush()` → додати знімки за `product_id`; не чіпати lazy-зв'язки в async |
| Фора повертає 6 товарів замість 37 | Пошук Фори вимагає збігу **всіх** слів | Надсилати лише головне слово, фільтрувати локально |
| «Томати у власному соку» у видачі на тунець | Релевантність рахує частку слів, перше не обов'язкове | Перше слово запиту — обов'язкове |
| Сільпо і Novus не зіставляються | Novus віддає GTIN-14 з провідним нулем | Нормалізувати до 13 цифр з перевіркою контрольної цифри |
| `TelegramBadRequest: can't parse entities` | `<` чи `&` у назві товару при `parse_mode=HTML` | `html.escape` для всього, що прийшло ззовні |
| `TelegramBadRequest: message is not modified` | Натиснули ту саму сторінку ще раз | Ігнорувати саме цю помилку |
| Метрики Prometheus «вибухають» | `path` = сирий URL з `search_id` | Брати шаблон маршруту з `request.scope["route"].path` |
| `api` стартує раніше за міграцію | `depends_on` без `condition` | `condition: service_completed_successfully` |
| Тести з SQLite падають на `database is locked` | Спільне з'єднання між корутинами | `NullPool` для SQLite у тестах |

## 🎤 Interview Prep

| Питання | Де ти це робив | Ключові слова |
|---|---|---|
| Різниця liveness і readiness? Що перевіряти в кожній? | `/healthz` vs `/readyz` | каскадні рестарти, залежності, трафік |
| Як інтегруватись з нестабільним стороннім API? | Адаптери мереж | таймаут на виклик, семафор, часткова відповідь, не кешувати невдачу |
| Навіщо черга і окремий воркер? | Штрихкоди Сільпо | latency користувача, producer/consumer, ідемпотентність, dedupe |
| Чому міграції — окремий крок, а не при старті застосунку? | `migrate` у Compose | гонка реплік, one-shot, Job / Helm hook |
| Чому один образ для трьох процесів? | api / worker / bot | одна збірка, один скан, однакова версія |
| Що таке build once, deploy many? | `promote-staging` | тег `sha-…`, retag, digest, approve |
| Чому бот не можна масштабувати горизонтально? | Break-it #1 | long polling, `409 Conflict`, webhook |
| Що таке кардинальність метрик? | middleware API | labels, шаблон маршруту, пам'ять Prometheus |
| Як не закомітити секрет? | pre-commit | gitleaks, `.env` у `.gitignore`, `.env.example` |

**STAR-історія:** *«Сервіс збирає ціни з трьох сторонніх API, які я не контролюю. Одне з них не віддає штрихкод у пошуку — лише окремим запитом на товар. Щоб не змушувати користувача чекати, я виніс збагачення у фоновий воркер з чергою Redis і дедуплікацією; пошук повертається за ~1 с, а зіставлення товарів між мережами покращується з кожним пошуком. Падіння будь-якої мережі видно в метриках і показується користувачу, але не ламає відповідь.»*

**Питання інтерв'юеру:** як у вас обробляють збої сторонніх інтеграцій — є circuit breaker, алерти на зміну формату відповіді?
